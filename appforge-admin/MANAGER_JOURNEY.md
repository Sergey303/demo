# Клиенты, заявки и задачи — рабочий день руководителя

Внутренняя продуктовая спецификация. Дополняет DEMO_PRODUCT_BRIEF.md.
Гипотеза о потребностях небольшой вымышленной сервисной компании, а не
результат интервью, рыночного исследования или клиентского внедрения.
Не публиковать как готовую функциональность до прохождения приёмки.

## 1. Ради каких решений открывают приложение

| Момент | Вопрос руководителя | Действие | Нужная информация | Цена ошибки |
|---|---|---|---|---|
| Утро | Что поступило, но ещё не организовано? | Открыть заявку, добавить задачи | Клиент, описание, приоритет, число задач | Запрос забыт |
| Распределение | Какая работа осталась без исполнителя? | Назначить сотрудника | Задача, связанная заявка, текущие поручения | Работа стоит |
| В течение дня | Где работа не закончена, кому уточнить статус? | Открыть заявку и задачи | Фактическое состояние каждой задачи, исполнитель, комментарий | Обещания клиенту без основания |
| Звонок клиента | Что уже сделали по его обращению? | Найти клиента, затем заявку | История обращений, результат каждой работы | Повторное выяснение, неверный ответ |
| Конец дня | Что выполнено, что ещё требует действий? | Проверить результаты и незакрытые работы | Состояние задач и комментарии | Незавершённость скрыта за общим статусом |

Руководитель не обязан быть диспетчером. В демо три переключаемых
рабочих представления одной модели; это не права доступа.
[OPERATOR_JOURNEYS.md](OPERATOR_JOURNEYS.md) задаёт передачу работы
между диспетчером, исполнителем и руководителем. Будущие реальные
роли проверяются на сервере.
Загрузка сотрудника на P1 означает количество открытых поручений, а не
занятость в часах, производительность или достаточность ресурсов.
Не выводить выручку, прибыль, SLA и финансовый ущерб из счётчиков задач.

## 2. Сценарий, который продаёт ценность, а не количество экранов

Первый экран — «Что требует внимания». Уже есть учебные данные.
Сначала не заставлять создавать клиента и заявку. Посетитель за 30–60
секунд устраняет конкретный пробел, видит изменение и историю.
Полный сценарий создания остаётся вторичным (2–4 минуты; целевые
длительности UX, не измеренные результаты).

Демо-снимок: 3 клиента, 4 заявки, 5 задач. Имена условные.

| ID | Клиент | Заявка | Приоритет | Задачи (название; исполнитель; состояние; результат) |
|---|---|---|---|---|
| R1 | Альфа Сервис | ТО оборудования | Обычный | Осмотр; Анна; Выполнена; осмотр завершён, замечаний нет. Проверка запуска; Илья; В работе; проверка ещё не завершена |
| R2 | Север Проект | Настройка контроллера | Высокий | Согласование конфигурации; не назначен; Новая; пусто |
| R3 | Маяк | Диагностика привода | Обычный | Диагностика; Марина; Выполнена; причина учебного сбоя определена. Проверка результата; Марина; Выполнена; учебная проверка завершена |
| R4 | Альфа Сервис | Проверка насоса | Высокий | Нет задач |

Начальная сводка:
- 3 незавершённые заявки (R1, R2, R4);
- 1 заявка без задач (R4);
- 1 незавершённая задача без исполнителя (R2);
- 1 заявка, по которой все работы выполнены (R3);
- открытые поручения: Илья — 1, Анна/Марина — 0, без исполнителя — 1.
Сводки являются пересекающимися фильтрами разного уровня, их нельзя
складывать. Выводить единицу измерения рядом с числом. Не хардкодить
ожидаемые счётчики в UI; значения выше — эталон для тестов.

### Быстрый маршрут руководителя

M01: открыть «Задачи без исполнителя» → R2, назначить Анну;
переключиться на представление исполнителя Анна и начать работу.
Счётчик без исполнителя 1 → 0; у Анны открытых поручений 0 → 1;
R2 «Новая» → «В работе»; открытых заявок всё ещё 3.

M02: завершить поручение R2, указав результат «Конфигурация согласована».
Открытых поручений Анны 1 → 0; открытых заявок 3 → 2;
заявок со всеми выполненными работами 1 → 2. Открыть карточку
Север Проект и увидеть R2 и тот же комментарий.

M03: открыть R4 из «Заявки без задач», добавить работу «Осмотр насоса»,
назначить Илью; счётчик заявок без задач 1 → 0; открытых поручений
Ильи 1 → 2; состояние R4 остаётся «Новая», пока задача не начата.
Показать следующие доступные действия и CTA заказа.

M04: сбросить демо с подтверждением → исходные 3/1/1/1 и 5 задач.

### Исключения и контроль

- Частичное выполнение R1 не означает выполнение всей заявки.
- Изменение статуса на выполненный — осознанное действие; результат
  работы (Note) обязателен при завершении в этом демонстрационном процессе.
  При пустом результате показать конкретную ошибку, не менять счётчики.
- «Работы выполнены» не означает принятие клиентом, выставление счёта,
  оплату, фактическое качество или закрытие договора.
- Корректировка выполненной задачи обратно в работу — явное действие
  с подтверждением; результат сохраняется, состояние заявки и сводка
  пересчитываются. История изменений и production-аудит вне P1.
- Без исполнителя нельзя начинать/завершать работу в рамках этого сценария.
  Новая задача может быть неназначенной; смена исполнителя не завершает её.
- Приоритет — выбранная характеристика заявки, а не срок. В P1
  сортировать высокий раньше обычного, без придумывания просрочки.
- Пустой фильтр «без исполнителя» говорит «Все открытые задачи назначены»,
  а не «Данных нет» и не «Все заявки обработаны».

## 3. Рабочее место, а не галерея CRUD

Первый экран: заголовок «Что требует внимания», 4 компактных вычисляемых
счётчика, очередь действий. Из каждого числа открывается соответствующий
список с сохранённым фильтром. Строка: клиент, заявка, действие,
приоритет, исполнитель/пустое значение. Одно главное действие в строке.
Сортировка: высокий приоритет, затем стабильный порядок записей.
Сводка поручений по исполнителям вторична; не называть её утилизацией.

Карточка заявки: клиент-ссылка, название, приоритет, описание,
вычисляемое состояние, задачи с исполнителями и результатами.
Переход к клиенту не должен терять изменения; отмена формы не сохраняет.
Карточка клиента: данные и связанные заявки, завершённые и открытые,
без смешивания чужих записей. Общий поиск — по клиенту и названию
заявки; отдельный фильтр задач. Видимые метки фильтра и очистка.
В рабочем списке не показывать GUID вместо названий.
Сохранение/ошибка/отмена должны иметь понятную обратную связь.

Мобильный экран: одна колонка, основные действия без горизонтального
скролла, второстепенные поля по раскрытию. Не дублировать всю таблицу
на главном экране. Сначала карточка действия, потом подробности.

## 4. Что продаёт демо и кому оно не подходит

| Ситуация заказчика | Что показать | Первый оплачиваемый результат |
|---|---|---|
| Руководитель ежедневно выясняет статусы в чатах | Очередь действий, карточка заявки, история | Реестр обращений с двумя согласованными состояниями и одним рабочим списком; точный объём по смете |
| Диспетчер вручную распределяет поручения | Назначение, фильтр открытых поручений | Экран распределения на согласованном основании |
| Клиенту долго отвечают на вопрос о выполнении | Карточка клиента и результаты работ | Экран истории, связанный с одним источником данных |
| IT-команда уже имеет CRM/ERP | Один связанный сценарий и технические доказательства | Дополнительный модуль/интеграция, не замена всей системы |

Если коробочная CRM или уже имеющийся инструмент закрывает потребность
с приемлемой настройкой, не навязывать разработку. Ищем те процессы,
где важны собственные поля, действия, ограничения, интеграции либо UX.
Если нужна готовая бухгалтерия, складской учёт, маршрутизация или
планирование мощностей, не обещать эти функции этим демо.

## 5. Что измерять после знакомства с заказчиком

Предложить вместе определить одну исходную метрику и способ проверки:
время поиска статуса (секунды на выборке одинаковых запросов), число
обращений без назначенного следующего действия (по согласованному
определению и периоду), доля выполненных работ с зафиксированным
результатом. Не считать деньги из этих величин без данных о стоимости
и частоте; не обещать экономию. Это гипотезы для квалификации,
не результаты проведённого эксперимента.

## 6. Границы реализации

P1: три сущности, связи, выбор по имени, единый источник данных,
статусы и результат задач, очереди, тесты M01–M04, D01–D10 и O01–O14.
Проверить, как выразить инварианты имеющимися средствами AppForge.
Если P1-правило не обеспечено генерацией, явно выделить
потребительскую бизнес-логику и проверить отдельно; не править generated/.
Одинаковая семантика локального адаптера и живой реализации для
проверяемых действий; иначе маркировать расхождение и не публиковать
сценарий как доказательство работающего сервера.

P2: сроки, календарь, блокировки и причины ожидания, отдельная приёмка
работы, реальные роли, история изменений, плановая загрузка, уведомления.
Наличие срока само по себе не определяет просрочку: согласовать
часовой пояс, рабочие дни, перенос, момент завершения и правила SLA.
Не добавлять весь P2 до проверки коммерческой ценности P1.

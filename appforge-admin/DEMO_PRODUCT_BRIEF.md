# Внутренние системы под бизнес-процесс — спецификация демонстрации

Статус: проект развития, не описание уже готовых возможностей.
Публичное название: «Клиенты, заявки и задачи». Сервисная компания —
вымышленный пример, применимый к разным видам внутреннего учёта.
Заказчик покупает приложение и согласованные инженерные работы.

[MANAGER_JOURNEY.md](MANAGER_JOURNEY.md) — приоритетный рабочий маршрут,
эталонные данные, вычисляемые очереди и проверки M01–M04.
Он уточняет P1; продуктовые потребности пока являются гипотезами.

## 1. Цель и границы

После демонстрации руководитель должен понимать, каким может быть его
собственное рабочее приложение: как информация о клиенте превращается
в поручение сотруднику, где виден результат и как найти незавершённую работу.
Не нужно изучать техническую документацию для прохождения.

Сейчас на /demos/appforge/ доступны только реестр клиентов и отдельный
оригинальный сгенерированный Customer UI с локальным адаптером.
Три бизнес-сущности в business-operations.md (Customer, ServiceRequest,
WorkItem) и их CRUD-контракты/страницы сгенерированы, но лишь Customer
прошёл живой браузерный маршрут с БД. Статус заявки, срок, переходы между
статусами, экран руководителя и разные роли не являются готовыми
проверенными функциями данного демо.

P0 — улучшить вход и коммерческий путь существующего реестра.
P1 — сквозной рабочий сценарий с тремя связанными сущностями.
P2 — дополнительные требования только после приёмки P1.

## 2. P0 — существующая демонстрация

Первый экран: «Как может выглядеть внутреннее приложение вашей компании».
Один главный CTA «Попробовать реестр клиентов», короткое объяснение задачи,
вторичная ссылка на оригинальный интерфейс и технические доказательства.
Не помещать механизм генерации, исходный MD, производственные показатели,
время генерации и LLM в основной коммерческий маршрут.

Пользователь без регистрации выбирает заполненную учебную запись, создаёт
свою, находит, изменяет и удаляет её. После сценария — «Обсудить вашу
внутреннюю систему». Возврат к Engineering на согласованном базовом пути
хостинга; не хардкодить неизвестный публичный домен. Технические доказательства
по ссылке, с ясным разделением локальной модели и ранее выполненного
Chromium/API/PostgreSQL-теста. Не выдавать английский UI за локализованный.
Согласовать текст коммерческого wrapper с этим документом; текущий wrapper
ещё требует обновления.

## 3. P1 — сценарий «От заявки клиента до выполненной работы»

### Персона и данные

Вымышленная компания по обслуживанию оборудования, небольшой коллектив.
Диспетчер принимает запрос, руководитель распределяет работу, исполнитель
отмечает результат. В публичном демо пользователь может пройти все действия
одним учебным профилем; это НЕ доказательство разграничения полномочий.

Точный набор и начальные значения — в MANAGER_JOURNEY.md. Три клиента,
четыре заявки, пять задач. Есть заявка без задач, неназначенная задача,
частично выполненная и полностью выполненная заявка. Числа вычислять
из записей. Быстрый маршрут M01–M04 — основной, D01–D10 — расширенный.

### Рабочие экраны

- Главная: незавершённые заявки, заявки без задач, открытые задачи без исполнителя, заявки со всеми выполненными работами;
  переходы на соответствующий фильтр. Краткие подсказки и исходный сценарий.
- Клиенты: поиск, создание, изменение, открытие карточки с заявками.
- Заявки: список с клиентом, названием, приоритетом и вычисляемым состоянием,
  поиск, фильтр, создание с выбором клиента по имени (не ввод GUID).
- Карточка заявки: описание, ответственный за выполнение через задачи,
  список связанных задач, добавление задачи, история/результат.
- Задачи: название, заявка, исполнитель, состояние, комментарий.
  Фильтр «Мои задачи» только если явно задан учебный исполнитель;
  не изображать подлинный контроль доступа.

Первые два приоритета — навигация между сущностями и понятные связи.
Не добавлять календари, счета, чат, отчёты ради красоты.

### Модель и инварианты

Исходные поля: Customer(Name, Email, Segment, Note);
ServiceRequest(CustomerId, Title, Priority, Description);
WorkItem(ServiceRequestId, Title, Assignee, Status, Note).
Проверить поддержку lookup и ограниченных наборов статусов в актуальном
генераторе до изменения executable MD. Не изменять вручную generated/.

Предлагаемый минимальный набор статусов задачи: «Новая», «В работе»,
«Выполнена». Состояние заявки для P1 вычисляется из задач:
без задач — «Новая»; все задачи выполнены и хотя бы одна есть — «Работы выполнены»;
иначе при наличии начатых/выполненных задач — «В работе»; иначе «Новая».
Это демонстрационное правило, не универсальный процесс компании.
Не вводить редактируемый дублирующий статус заявки без необходимости.
Пустая обязательная строка и несвязанный FK не допускаются.
Не разрешать потерю дочерних записей при удалении клиента/заявки:
сначала проверить поведение generated API; если безопасной политики нет,
не предоставлять удаление связанных родительских записей в сценарии.
Задачи и заявки в разных представлениях читают один источник данных.
Ручная корректировка результата не должна приводить к рассинхронизации.
Для начала и завершения задачи обязателен исполнитель; при завершении —
непустой результат в Note. Возврат выполненной задачи в работу подтверждается.
Это правила P1, а не уже реализованные возможности. «Работы выполнены»
не означает приёмку клиентом или оплату.

### Маршрут посетителя

| Шаг | Действие | Видимый результат |
|---|---|---|
| D01 | Открыть демо без ввода | Видна заполненная сводка и реальные учебные записи |
| D02 | Открыть клиента | Видны связанные заявки, не данные других клиентов |
| D03 | Создать заявку «Осмотр компрессора», выбрать клиента и приоритет | Одна запись в списке и в истории клиента |
| D04 | Открыть заявку, добавить задачи «Осмотр» и «Согласование результата» | Обе связаны с этой заявкой |
| D05 | Назначить исполнителей обеим задачам, первую перевести в работу | В списках и сводке отражён тот же результат |
| D06 | Завершить одну задачу с результатом | Заявка остаётся в работе |
| D07 | Завершить вторую с результатом | Все работы выполнены; счётчики обновились |
| D08 | Найти результат по клиенту и названию | История и сводка согласованы |
| D09 | Сбросить учебные данные | Исходная картина восстановлена |
| D10 | Нажать CTA заказа | Переход к услуге Engineering без регистрации |

Негативная приёмка: пустые обязательные поля; несуществующая связь;
повторное быстрое сохранение; отмена редактирования; фильтр без результата;
обновление страницы с ясным поведением хранения; сброс; отсутствие
реальных сетевых запросов из публичного симулятора, мобильная ширина 390 px,
клавиатура и видимая обратная связь. Не утверждать, что публичная имитация
доказывает серверную конкурентность.

## 4. Технические требования к реализации

Применить существующий AppForge, не писать вручную второй CRUD-каркас.
Начать с исходного business-operations.md, проверить доступные средства
отношений/форм/closed sets. Сначала новая отдельная сборка и preflight,
затем штатная генерация, проверка контрактов, TypeScript/.NET и изолированный
живой тест связанных операций на тестовой БД. Хранить версию генератора,
входную модель, результат теста и ограничения. Не затирать проверенную
предыдущую сборку. Если генератор не поддерживает нужную возможность,
оформить небольшой consumer-neutral пробел отдельно, не выдавать
вручную сделанный экран за результат генерации.

Публичная версия: исходные сгенерированные компоненты и локальный
демонстрационный адаптер для всех трёх сущностей; тонкий явно маркированный
слой навигации/сводки допустим. Согласовать локализацию отдельно.
Никакого публичного API/БД, приватного генератора, секретов или реальных
данных. Не подключать авторизацию имитацией production-ролей.
Взаимосвязанные изменения проверять в браузере, тесты включить в smoke.
Не изменять GosVet, Reliable Jobs и Enterprise AI.

## 5. P2 — не блокирует продажу

Сроки выполнения и просрочка (с согласованным правилом дат/часовых поясов),
реальные роли и серверные проверки доступа, аудит изменений, интеграции,
дополнительные отчёты — отдельные требования, когда показана польза P1.
Никаких обещаний этих функций в карточке P0. Видеозапись и скриншоты
нового процесса только после фактической приёмки; предыдущие снимки
подписывать как Customer CRUD, а не сквозной процесс.

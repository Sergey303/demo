# Клиенты, заявки и задачи — диспетчер и исполнитель

Статус: требования к P1, не описание реализованного приложения.
Дополняет DEMO_PRODUCT_BRIEF.md и MANAGER_JOURNEY.md.
Персоны, трудности и целевые длительности — гипотезы для обсуждения
с заказчиком, а не результаты наблюдения за реальной компанией.

## 1. Общая цель

Руководитель видит состояние работ только тогда, когда сотрудникам
удобно и выгодно фиксировать его в процессе выполнения. Не заставлять
диспетчера повторно вводить данные клиента, исполнителя — искать
поручение среди чужих записей, а руководителя — переписывать их статусы.

Три рабочих представления одного приложения и одного набора данных:
«Руководитель», «Диспетчер», «Исполнитель». Это переключатель учебного
рабочего места, а не вход в аккаунт, назначение полномочий или
проверка безопасности. В P1 нет реальной идентификации исполнителя,
ограничения доступа или tenant isolation. Идентичность учебного
исполнителя видна явно; переключение профиля само по себе не меняет
записи. Все экраны демонстрируют один бизнес-процесс.

## 2. Рабочее место диспетчера

### Задачи

| Ситуация | Вопрос | Действие | Что мешает |
|---|---|---|---|
| Поступил звонок | Кто клиент, не было ли такого обращения? | Найти клиента, увидеть его заявки | Повторный ввод, забытая предыдущая заявка |
| Новый запрос | Что именно требуется и насколько срочно? | Создать заявку | Длинная форма, обязательные неизвестные данные |
| Нужно организовать работу | Какой следующий шаг и кто его выполнит? | Добавить задачу, назначить сотрудника | Ввод GUID, уход в другой реестр |
| Клиент уточняет статус | Что уже выполнено, что остаётся? | Открыть заявку, прочитать результат | Переписка с каждым исполнителем |
| Передача смены | Какие заявки ещё не организованы? | Открыть очереди без задач/исполнителя | Неполная передача информации |

### Первый экран

Заголовок «Приём и распределение заявок».
Главное действие «Новая заявка»; быстрый поиск по клиенту и
названию заявки. Ниже две очереди: заявки без задач (R4) и задачи
без исполнителя (R2). Каждая карточка показывает клиент, заявку,
приоритет и конкретное следующее действие. Приоритет высокий
выше обычного, затем стабильный порядок. Отдельно — список всех
заявок с фильтром и состоянием; не выводить его целиком на
главном экране.

### Приём обращения

Шаг A. Выбрать клиента по имени из списка с доступными учебными
записями. При совпадающих названиях показать дополнительный
безопасный признак (сегмент или учебный ID), не выбирать
автоматически. Если клиента нет, предложить создать карточку
и вернуться к незавершённой форме. Не считать совпадение имени
доказательством дубля и не объединять записи автоматически.
Шаг B. Название заявки (обязательно), приоритет (по умолчанию
обычный), описание (необязательно). Не требовать email,
телефон, срок, адрес, договор, цену или назначение до регистрации
обращения. Показывать историю открытых заявок выбранного клиента,
чтобы заметить возможный повтор; не блокировать обоснованный новый
запрос.
Шаг C. «Сохранить заявку». Только после подтверждённого сохранения
показать карточку и доступные действия «Добавить задачу» / «К списку».
Не создавать пустую задачу автоматически. Заявка без задач допустима
и сразу появляется в очереди диспетчера/руководителя.
Шаг D. Добавить задачу: название обязательно, исполнитель может
быть не назначен, начальное состояние «Новая». Из карточки заявки
связь уже известна, поле заявки повторно не запрашивается. Выбор
исполнителя по имени из учебного справочника Анна, Илья, Марина;
пустой вариант «Не назначен». Назначение не равно началу работы.
После успешного сохранения показать результат в карточке и очередях.

При ошибке оставить введённые значения, фокусировать проблемное поле;
отмена не меняет сохранённых записей. Двойной клик не должен
создавать вторую запись в публичном адаптере; это не доказательство
серверной идемпотентности. Если пользователь покидает изменённую
форму, предупредить о несохранённых изменениях.

Цель UX (подлежит измерению): регистрация известного клиента с
простым обращением за 30–60 секунд без чтения инструкции;
из R2 до назначения — не более двух осмысленных действий
после открытия карточки (выбрать исполнителя, сохранить).

## 3. Рабочее место исполнителя

### Задачи

| Ситуация | Вопрос | Действие |
|---|---|---|
| Начало работы | Что поручено мне? | Открыть «Мои задачи» |
| Получено поручение | Что требуется, по какой заявке? | Открыть карточку задачи и контекст |
| Начал | Как сообщить об этом без переписки? | «Начать работу» |
| Завершил | Как передать результат без повторного ввода? | Вписать результат, подтвердить выполнение |
| Обнаружена ошибка | Как вернуться к работе? | Явно вернуть выполненную задачу в работу |

### Первый экран

Явный селектор учебного исполнителя; по умолчанию Илья,
у него есть открытая задача R1 «Проверка запуска».
Список «Мои открытые задачи»: высокий приоритет заявки раньше
обычного; в рамках одинакового приоритета сначала «В работе»,
затем «Новая», далее стабильный порядок. Отдельно — выполненные
задачи. При пустом списке: «У выбранного исполнителя нет открытых
поручений», а не «Все работы компании выполнены».
Не показывать ему сводку всей компании и поля, которые не нужны
для выполнения. Возможность переключить учебный профиль открыта
и помечена как демонстрационная; это не разграничение доступа.

### Карточка задачи

Заголовок задачи, состояние, приоритет родительской заявки,
клиент, название заявки, её описание (по раскрытию), исполнитель,
сохранённый комментарий/результат. Не вводить эти данные повторно.
Ссылка на родительскую заявку — в контекст, а не в новый черновик.
Главное действие зависит от состояния: «Начать работу» (Новая),
«Завершить с результатом» (В работе), «Вернуть в работу»
(Выполнена, вторичное действие с подтверждением).

Завершение — компактная форма: поле «Результат работы»,
предзаполнено ранее сохранённым Note, если он есть; исполнитель
может изменить текст. Не завершать по одному открытию формы.
При пустом или пробельном тексте — ошибка; при успехе сохранение
результата и статуса одной согласованной операцией. Если форма
закрыта без сохранения, статус/Note не меняются. После успешного
действия обновить список, показать «Работа выполнена» и переход
к следующему поручению; в истории клиента виден тот же результат.
Отличать завершение работы от приёмки, качества, оплаты.

P1 не содержит отдельной отметки ожидания, частичной трудоёмкости,
чек-листа оборудования, геопозиции, фото, мобильного офлайн-хранилища,
уведомлений и SLA. Это не обязательные требования ко всем заказчикам.
Для ожидания в P1 можно оставить комментарий, статус остаётся
«В работе»; отдельный статус и причина ожидания — P2.

Цель UX: начать поручение одним действием после открытия карточки;
завершить — заполнить один результат и подтвердить. Проверить на
390 px, не заставлять прокручивать широкие таблицы. Все действия
доступны с клавиатуры и имеют видимую обратную связь.

## 4. Контракт совместного рабочего процесса

Состояния задачи: Новая, В работе, Выполнена.
Допустимые переходы в P1:

| Операция | Предусловия | Эффект |
|---|---|---|
| Создать | Существующая заявка, непустое название | Новая, исполнитель необязателен |
| Назначить/переназначить | Новая либо В работе, выбран существующий учебный исполнитель | Меняется исполнитель, не состояние |
| Снять назначение | Только Новая | Исполнитель пуст, задача в очереди без исполнителя |
| Начать | Новая, исполнитель назначен | В работе |
| Завершить | В работе, исполнитель назначен, непустой результат | Выполнена + сохранённый Note |
| Вернуть в работу | Выполнена, подтверждение | В работе, прежний Note сохраняется |

Не позволять обычному CRUD-редактору менять состояние в обход
этого контракта. Выполненную задачу не переназначать без возврата
в работу. Новая задача не может перейти сразу в «Выполнена»:
сначала начать. При отклонённом переходе запись и агрегаты
остаются прежними. Сохранение результата и статуса атомарно
в живой реализации; в симуляторе единая мутация состояния.
Действия ролей — демонстрационные сценарии, не серверная ACL.

Состояние заявки вычисляется по всем связанным задачам согласно
DEMO_PRODUCT_BRIEF.md. Добавление новой задачи к полностью
выполненной заявке снова делает её открытой («В работе»,
так как имеются выполненные и новая задача); перед действием
показать явное подтверждение изменения состояния. Не создавать
второй редактируемый статус заявки. Счётчики и фильтры строить
из единого набора записей, не хранить отдельно.
Смена профиля и маршрута не сбрасывает данные. Обновление страницы
для публичного адаптера: сохранять текущий ранее заявленный
режим памяти (полная перезагрузка возвращает исходные данные);
сообщить об этом в демо. Сброс из UI требует подтверждения.

## 5. Сквозной демонстрационный маршрут O01–O10

Начальное состояние — эталон MANAGER_JOURNEY.md: 3 клиента,
4 заявки, 5 задач. Незавершённые/без задач/без исполнителя/
работы выполнены = 3/1/1/1. Не добавлять новый независимый seed.

| Шаг | Рабочее место и действие | Проверяемый результат |
|---|---|---|
| O01 | Диспетчер: открыть R2 из неназначенных | Карточка Север Проект; правильная задача |
| O02 | Назначить Анну, сохранить | Задача Новая; сводка 3/1/0/1, у Анны 1 открытая |
| O03 | Переключить исполнителя Анна, открыть «Мои задачи» | Видна R2; чужие задачи отсутствуют в этом фильтре |
| O04 | Начать R2 | В работе; сводка не меняется |
| O05 | Попытаться завершить с пустым результатом | Ошибка, статус и счётчики прежние |
| O06 | Ввести «Конфигурация согласована», завершить | Выполнена, R2 работы выполнены, сводка 2/1/0/2 |
| O07 | Руководитель: открыть историю Север Проект | Тот же результат, у Анны 0 открытых |
| O08 | Диспетчер: открыть R4, добавить «Осмотр насоса», назначить Илью | Сводка 2/0/0/2; R4 Новая; задач 6, у Ильи 2 открытые |
| O09 | Исполнитель Илья: открыть задачи | Две открытые задачи; Анна не показывается в фильтре |
| O10 | Сбросить с подтверждением | Восстановлены 3/1/1/1, 5 задач и исходный профиль |

Отдельная проверка O11–O14 (после сброса):
- O11: диспетчер создаёт обращение известного клиента, отменяет
  добавление задачи, заявка попадает в очередь без задач. Проверить
  новую запись в карточке клиента; после добавления задачи исчезает
  из очереди без задач. При неизвестном клиенте проверить возврат
  к черновику после создания клиента.
- O12: исполнитель не может начать неназначенную задачу, завершить
  новую без начала, переназначить завершённую или снять исполнителя
  с начатой. В живой реализации проверить также API, не только UI.
- O13: завершить R2 по O01–O06, возвратить в работу с подтверждением:
  прежний результат сохранён; R2 снова открыта; 3/1/0/1.
  Отмена подтверждения ничего не меняет.
- O14: проверить добавление задачи в R3: при отмене подтверждения
  прежний набор; при согласии R3 снова открыта. Смена рабочего
  места, поиск, отмена формы и повторный клик не теряют данные.

M01–M04 и D01–D10 остаются регрессиями, но быстрый коммерческий
маршрут показывает передачу между рабочими местами, а не ручную
смену статуса руководителем от имени сотрудника. Перед D07 начать
вторую задачу; для M01 начало допускается в представлении исполнителя.

## 6. Приёмка и бизнес-ценность

Техническая реализация — по DEMO_PRODUCT_BRIEF.md. Уточнить
возможности генератора для связанных форм и переходов, не писать
вручную второй CRUD-каркас. Потребительский слой рабочих мест
и правил явно выделен, проверяется отдельно; generated/ не
редактировать. До живого теста не заявлять серверную реализацию
переходов, ролей, конкурентности или защиты данных.

Коммерческая проверка: показать один короткий маршрут — диспетчер
назначил, исполнитель выполнил, руководитель увидел результат.
Спросить, где в бизнесе заказчика сейчас приходится повторно
вводить сведения, вручную выяснять статус или подтверждать
выполнение; какие действия можно убрать и какой первый экран
имеет самостоятельную ценность. Не требовать менять весь процесс
ради демо. Не рекламировать генератор, его экономику или токены.

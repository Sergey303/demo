# Reliable Jobs — технический режим для CTO и архитектора

27.11.2026. Спецификация P1, не отчёт о новом тестировании.
Публичный интерфейс — модель, а не консоль реальной БД.
Источники текущей реализации: README.md, sql/001_init.sql,
src/Program.cs (/jobs), src/OutboxWorker.cs, src/JobLogic.cs,
tests/smoke.py, tests/ConcurrencyIntegrationTests.cs, tests/JobLogicTests.cs.
Границы: текстовые jobs, не отдельные audio/document workflows.

## 1. Что должен решить технический покупатель

| Вопрос | Что предъявляем | Чего это не доказывает |
|---|---|---|
| Где находится точка принятия? | Commit job + outbox до ответа 202 | Что отправитель получил ответ |
| Как исключена гонка двух POST? | UNIQUE(idempotency_key), INSERT ON CONFLICT, ReadCommitted, один ID | Единственность при разных ключах или после удаления ключа |
| Как связаны обработка и результат? | Одна транзакция result + processed_at, SQL locks | Один вызов обработчика или однократный внешний эффект |
| Что случится после отказа? | Различие отказа до commit, неопределённого commit и потери ответа | Автоматическое восстановление при любой недоступности |
| Как оператор узнает о проблеме? | queued/done/failed, attempts, last_error, next_attempt_at | Готовый мониторинг, алерты и SLA |
| Почему можно доверять исполнителю? | Проверяемые инварианты, исходники, матрица доказательств и честные пробелы | Общая сертификация или production-аудит |

Покупатель должен за 2–3 минуты (цель UX, не измерение) выбрать
инвариант, воспроизвести контрпример или отказ и открыть подтверждение.
Не вынуждать читать полный исходник и не показывать зелёную галочку
как эквивалент гарантии. Вход из бизнес-сценария; техническое раскрытие
не сбрасывает модель и не меняет её состояния.

## 2. Структура экрана

Верх: выбранный сценарий, исходный ключ и payload, активная сторона,
фаза транзакции. Явная плашка «Симуляция; не подключено к PostgreSQL».
Далее четыре раскрываемые зоны:

1. Трасса: отправитель → HTTP API → PostgreSQL → Worker → GET.
   Пронумерованные события, причинно-следственные связи, границы
   транзакций T1/T2. Без вымышленных реальных timestamps, скорости,
   корреляционных ID из production. Временная шкала условная.
2. Состояние: отдельные committed snapshots jobs и outbox,
   отдельная карточка знания отправителя. Незавершённые изменения
   показывать только как tentative, не добавлять к committed counts.
3. Контракт: метод, путь, условный request/response, status code,
   payload hash, ID. Известный ID у отправителя возникает только
   после получения ответа; не подставлять его из окна наблюдателя.
   Для неизвестного ID GET не предлагается.
4. Доказательства: выбранный инвариант, ожидаемое состояние,
   тип доказательства, дата и ссылка на конкретный файл. Технический
   режим не запускает реальные проверки и не меняет исторический статус.

Состояние и трасса должны быть выводом единой детерминированной модели,
а не отдельными заранее нарисованными карточками.
Реальные GUID заменены видимыми учебными JOB-001/EV-001; пометить это.
Хеш показывать только если фактически рассчитан над UTF-8 текстом;
иначе не показывать значение. Не вычислять фиктивный SHA-256.
При конфликте сохранять исходное содержимое; пробелы и переносы
не нормализовать при сравнении.

### Поля наблюдения

| jobs | outbox | Клиент |
|---|---|---|
| id, key, input, status, result | id, job_id, attempts, next_attempt_at, processed_at, last_error | исходный ключ, попытки POST, последний наблюдаемый ответ, известный ID |
| queued/done/failed | отсутствие processed_at не равно готовности к обработке: есть backoff и terminal | accepted не равно done |
| WordCount/Sha256 для реального text handler | last_error — тип исключения, не приватный текст | отсутствие ответа не равно отсутствие записи |

В симуляции допустим относительный виртуальный clock. Для ошибок
1–4 задержки 1/2/4/8 секунд, отображать как модель политики, а не
реальные замеры. Пятая ошибка — terminal; next_attempt_at отложен
до максимального времени в текущем коде (не обещать отдельный DLQ).
Симулятор может переходить к следующему разрешённому моменту одной
кнопкой без реального ожидания. Успешное выполнение не увеличивает
attempts; поле считает зафиксированные ошибки обработчика.

## 3. Инварианты и пределы

| ID | Инвариант | Условие и граница |
|---|---|---|
| I01 | Не более одной jobs записи на ключ | В одной БД, пока запись существует; не на бизнес-операцию при разных ключах |
| I02 | Приём job + outbox вместе | Для созданной /jobs операции; FK/UNIQUE сами по себе не гарантируют наличие outbox у произвольно вставленной jobs |
| I03 | Повтор с тем же ключом и содержимым возвращает прежний ID | Сравнивается SHA-256 текста; конфликт изменённого хеша — 409; POST 200 не обещает done |
| I04 | Результат и processed_at фиксируются вместе | Для штатной успешной транзакции text worker; не для внешнего API |
| I05 | Два worker не владеют одной строкой одновременно | Пока удерживается row lock; SKIP LOCKED не обеспечивает FIFO или fairness |
| I06 | Откатившийся claim вновь доступен | После освобождения блокировки и при выполнении условий выборки; не гарантия срока |
| I07 | SQL failure не расходует бюджет handler failure | Если транзакция откатилась; при неизвестном исходе commit сначала наблюдаем состояние |
| I08 | Пять зафиксированных handler failures ведут к failed | Текущий код откладывает событие, processed_at остаётся NULL; не перезапускать повтором POST |
| I09 | Повтор не меняет terminal result | Одинаковый ключ возвращает ID; GET различает done/failed |
| I10 | Внешний эффект требует отдельной защиты | Отдельное хранилище/транзакция получателя; контракт ключа, сверки и компенсации согласуется отдельно |

Три разных смысла «однажды»: одна принятая запись, один записанный
результат, одно фактическое внешнее действие. Первые два можно
проверять в рамках реализации; третье не следует из первых двух.
Даже при одном committed результате обработчик может быть вызван повторно.

## 4. Точки отказа и ожидаемые состояния

| Точка | Committed состояние | Что знает клиент / безопасный следующий шаг |
|---|---|---|
| T1 до INSERT | 0 job, 0 outbox | Нет подтверждения; повтор прежнего ключа |
| T1 после INSERT job до INSERT outbox, rollback | 0/0 после rollback | Нет подтверждения; прежний ключ |
| T1 после INSERT outbox до commit, rollback | 0/0 | Нет подтверждения; прежний ключ |
| T1 commit выполнен, HTTP-ответ потерян | 1/1; queued если worker ещё не обработал | Неизвестно; повтор прежнего ключа |
| T1 ответ commit потерян | 0/0 ИЛИ 1/1; неизвестно до наблюдения | Не утверждать rollback; повтор прежнего ключа |
| T2 claim удерживается | 1/1; queued, без committed result | Второй worker пропускает locked row |
| T2 result UPDATE выполнен, rollback до commit | queued, result NULL, processed_at NULL | Повтор claim после освобождения lock |
| T2 commit выполнен, подтверждение потеряно | done + result + processed_at | GET/чтение состояния, не повтор эффекта вручную |
| T2 commit неизвестен | queued или done (при успешном handler); состояние установить чтением | Не называть потерю соединения доказательством rollback |
| handler throws, запись ошибки committed | attempts+1; queued или failed | Смотреть статус/следующее разрешённое время |
| запись ошибки не committed | прежний attempts | Инфраструктурный отказ, а не новая зафиксированная попытка |
| Внешний эффект произошёл, ответ потерян | Локальная транзакция не устанавливает факт внешнего эффекта | Сверить получателя, не обещать безопасный повтор |

Уточнение к RJ06/RJ08: это именно подтверждённый rollback.
Не сводить неизвестный результат commit к rollback. В P1 достаточно
схемы двух возможных исходов для неопределённого commit; не добавлять
моделирование сетевых таймингов и случайности.

## 5. Матрица доверия

Типы: SOURCE (видно из кода), UNIT (проверка чистой логики),
PG-PRIMITIVE (реальная PostgreSQL, отдельные таблицы), HTTP-E2E
(реальный API + worker + БД), BROWSER-MODEL (модель), NOT TESTED.
Статус и тип независимы. SOURCE не PASS живого отказа.
Исторический PASS из README.md от 05.11.2026; не представлять
как результат запуска на текущем SHA. Тестов заново не проводили.

| Инвариант | Имеющиеся свидетельства | Не доказано |
|---|---|---|
| I01/I03 | HTTP-E2E smoke.py: 20 запросов, один ID, 409; PG-PRIMITIVE ConcurrentUniqueKeyClaimsHaveExactlyOneWinner | 20 отдельных TCP-соединений одновременно, потеря ответа, разные ключи одной бизнес-операции, срок хранения |
| I02 | SOURCE: Program.cs transaction, schema FK/UNIQUE | fault injection между INSERT job/outbox/commit, прямой подсчёт строк этим smoke |
| I04 | SOURCE: OutboxWorker; HTTP-E2E GET done и проверка WordCount/SHA256 | прямое утверждение о количестве result writes, процесс crash после result UPDATE |
| I05/I06 | PG-PRIMITIVE SkippedLockedWorkIsReclaimedAfterRollback: две строки/два соединения, явный rollback и reclaim | kill реального worker, реальный обрыв соединения, fairness |
| I07/I08 | SOURCE: граница catch; UNIT RetryPolicy/JobLogic | живое внесение SQL failure, terminal handler exhaustion |
| I09 | SOURCE: повтор POST не меняет записи | повтор POST после terminal failed/done в отдельном HTTP тесте |
| I10 | Ограничение архитектуры, схема | Любое обещание внешней однократности |

smoke.py отправляет 20 запросов через ThreadPoolExecutor(max_workers=10);
не заявлять 20 одновременно активных соединений. Он не проверяет
SQL count jobs/outbox, processed_at или точное число ответов 202.
Исторические 10/10 относятся к указанному запуску README, не выводить
их как текущий полный набор тестов (в репозитории есть AudioIdentityTests).
Показывать ссылки на файл/тест, дату, ожидаемое и фактическое
наблюдение; неподтверждённые строки помечать NOT TESTED.

## 6. Вопросы архитектурного выбора у заказчика

- Идентификатор: кто создаёт, где хранит, как различать повтор и новую
  операцию? Область tenant/operation и срок retention должны быть согласованы.
- Граница commit: где бизнес-состояние, где запись события? Если
  разные БД, transactional outbox одной БД не создаёт общий commit.
- Конкурентность: блокировка в БД, lease/fencing или другой механизм?
  Длительный внешний вызов внутри транзакции может удерживать locks;
  не переносить эту схему text handler автоматически на I/O.
- Доставка наружу: поддерживается ли idempotency key, inbox/dedup
  получателя, запрос состояния, сверка, компенсация? Что делать с
  неопределённым исходом, если получатель не предоставляет такого API?
- Эксплуатация: возраст очереди, backlog, retries, failed, latency,
  алерты, разрешённый re-drive, retention. Это требования к будущей
  системе, а не имеющийся production monitoring.
- Ограничения: нагрузка, зависимые сервисы, отказ БД/сети, RTO/RPO,
  права, конфиденциальность и регламент доступа. Не обещать SLA.

Не предлагать outbox как универсальный ответ. Если операция целиком
синхронна и атомарна в одной БД, может быть достаточно уникального
бизнес-ключа и безопасного повтора. Если есть асинхронная доставка,
сопоставить outbox/inbox, контракт внешнего API и сверку.
Выбор и стоимость изменения зависят от фактического процесса.

## 7. Приёмка технического режима T01–T08

T01: открыть раскрытие после RJ01, увидеть 1/1 committed,
неизвестный ID у отправителя и неизменный шаг.
T02: RJ02/RJ07 — один ID, 200/409; payload/hash неизменны.
T03: RJ06/RJ08 — rollback не выдаёт tentative изменения за committed;
в отдельной схеме неизвестного commit явно два допустимых исхода.
T04: RJ09 — результат и processed_at появляются вместе; повтор
обработки не меняет committed результат.
T05: RJ10 — виртуальные задержки 1/2/4/8, 5 committed failures,
failed без processed_at; нет restart по POST.
T06: RJ11 — различить HTTP 200 already-accepted и GET done/failed;
другая key создаёт отдельную операцию.
T07: открыть матрицу доказательств, проверить source/unit/primitive/
HTTP-E2E/model/NOT TESTED и корректные ссылки; no blanket PASS.
T08: RJ12 — отдельная граница внешнего эффекта, неизвестный исход,
нельзя выдать гарантированный безопасный повтор; закрытие панели
не меняет состояние; мобильный и клавиатурный сценарий.

В браузере не нужно реализовывать все точки T1/T2 как отдельные
интерактивные эксперименты. Для P1 достаточно общей модели RJ01–12,
таблицы точек, раскрытия транзакций и доказательств; T01–08 тестируют
семантику/видимость, а не реальные серверные отказы. P2 fault injection
согласовать отдельно (прокси/изолированный тестовый процесс,
наблюдение независимым соединением, никаких production failpoints).

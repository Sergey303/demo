# Reliable Jobs — продуктовая спецификация P1

Статус: проект, не реализованные возможности. Контекст и продажа:
COMMERCIAL-BRIEF.md. Существующая реализация: README.md, src/Program.cs,
src/OutboxWorker.cs, src/JobLogic.cs, sql/001_init.sql, tests/smoke.py.
Публичный сценарий: public-demos/build.py, ui.mjs, model.mjs, smoke.mjs.
Не изменять принятые GosVet, AppForge и Enterprise AI.

## 1. Что должен понять посетитель

«Если ответ потерян, я не знаю, принята ли операция. Повтор с новым
идентификатором может создать вторую работу. Повтор с прежним ключом
и теми же данными позволяет обнаружить уже принятую операцию.
Принята — ещё не значит выполнена. Внешний эффект — отдельная гарантия».

Показать пользу за 30–60 секунд (целевой UX, не замер).
Сценарий без регистрации, заполнен заранее. Не заставлять вводить ключ,
JSON, SQL или текст произвольной заявки до первого действия.

## 2. Учебная предметная область и границы

Отправитель — условная CRM; получатель — условный сервис обработки.
Запрос: «Заявка SR-1042 — Проверка насоса», стабильный учебный ключ
service-request-1042 (printable ASCII, 10–128 знаков), payload фиксирован.
Другая версия запроса: «Заявка SR-1042 — Проверка контроллера».
Публичный симулятор не обращается к сети и не хранит реальные сведения.
Условный результат «Заявка обработана» — бизнес-иллюстрация;
техническое доказательство настоящего сервиса — WordCount и SHA-256.
Не выдавать имитацию двух систем за их реальную интеграцию.

У отправителя: исходная операция, ключ, число попыток отправки,
статус наблюдения (не отправлено / подтверждение не получено /
принята / выполнена / ошибка / конфликт). Это статус знания
отправителя, а не обязательно состояние сервера.
У принимающей стороны: job ID, число принятых уникальных операций,
очередь, состояние queued/done/failed, число ошибок обработчика,
результат и отметка обработки. Состояние «обработка идёт» можно
показывать лишь как моделируемую фазу незавершённой транзакции,
не как состояние реального GET API.

Истина — одна модель состояния; журнал и счётчики выводятся из неё.
Не объединять число отправок, принятых записей и ошибок обработчика.
Данные отправителя не должны чудесным образом узнавать скрытое
серверное состояние: карточка «получатель» — отдельное видимое
посетителю окно наблюдения, явно подписанное.

## 3. Главный маршрут RJ01–RJ05

Начальное состояние: 0 отправок, 0 принятых, 0 результатов.
Два вида одного сценария: «Без защиты (учебная модель, каждая
отправка создаёт новую запись)» и «С защитой (модель стабильного
ключа и транзакций)». Одинаковые входные данные и точки отказа.
Не рисовать заранее дубли в защищённой ветке или прибыль в любой.

| Шаг | Действие | Без защиты | С защитой |
|---|---|---|---|
| RJ01 | Отправить с потерей ответа после commit | 1 принята, отправитель не знает | 1 принята, отправитель не знает |
| RJ02 | Повторить с прежними данными | 2 принятых, подтверждение новой записи | 1 принята, прежний ID, 200 already-accepted |
| RJ03 | Обработать ожидающие | 2 записанных результата | 1 записанный результат |
| RJ04 | Проверить состояние по известному ID | У последнего ID результат; дубль остаётся | GET: done, результат прежней операции |
| RJ05 | Обсудить аналогичную операцию | CTA к Engineering, не технический checkout | CTA к Engineering |

Сравнение выполняется параллельно одинаковыми действиями или
последовательно из одинакового reset; не смешивать хранилища.
Без защиты — намеренно примитивное контрфактическое поведение,
не измерение другого продукта. Если эта ветка слишком трудоёмка,
достаточно короткой статической схемы с тем же явно указанным
допущением; интерактивная защищённая ветка обязательна.

Первый экран: короткий вопрос «Ответ не пришёл. Отправлять снова?».
Две стороны, на каждой видно наблюдаемое/фактическое состояние.
Главная кнопка меняется по шагу; последняя не выполняет сетевой запрос.
Вторичные: «Другие отказы», «Как это проверено», «Сбросить».
Успех отображать не по HTTP 202/200, а после фактического
завершения и отдельной проверки статуса.

## 4. Остальные сценарии RJ06–RJ12

Каждый начинается со своего явно определённого состояния, сброс
с подтверждением при наличии действий. Никаких случайных отказов
или реального ожидания таймеров; время и backoff моделируются.

| ID | Отказ/действие | Ожидаемая защищённая ветка |
|---|---|---|
| RJ06 | Потеря до commit / откат при приёме | job=0, outbox=0, ответ не подтверждён; повтор тем же ключом создаёт 1 job + 1 outbox, 202 |
| RJ07 | Тот же ключ, изменённое содержимое | 409, первоначальный payload и ID неизменны, дополнительного outbox нет |
| RJ08 | Сбой при обработке до commit | Ранее принятая job остаётся queued; результат отсутствует, processed_at отсутствует, ошибки обработчика не увеличились |
| RJ09 | Восстановить и завершить | done, результат и отметка обработки записаны вместе; повтор обработки не меняет результат |
| RJ10 | Пять ошибок обработчика | 1–4: queued, видна очередная попытка; 5: failed, событие сохранено, автоматические попытки исчерпаны |
| RJ11 | Повтор POST после done или failed | 200 already-accepted, тот же ID; GET отличает done от failed; повтор не перезапускает failed |
| RJ12 | Внешний сервис выполнил действие, ответ потерялся | Демонстрация неопределённости: не обещать exactly-once; нужен отдельный договор идемпотентности получателя, проверка статуса/сверка |

RJ12 — короткая объясняющая интерактивная ветка или схема,
а не реализация внешнего API, не симуляция платежей.
Без достоверного способа выяснить результат система не должна
показывать гарантированно безопасный повтор. Компенсация
тоже отдельная операция и требует своего контракта.
Показывать не только «всё исправилось», но и честное состояние
«Требует проверки» при исчерпании попыток/неизвестном внешнем эффекте.
Не добавлять рабочую кнопку ручного перезапуска failed, поскольку
текущего серверного контракта для этого нет.

## 5. Технический режим

Раскрываемое объяснение после бизнес-сценария:
- POST /jobs: 202 новый, 200 ранее принят, 409 несовпадение payload.
- GET /jobs/{id}: фактический status и result, не обещание доставки
  наружу. HTTP 200 для GET не означает status=done.
- Одна транзакция для job + outbox, уникальный ключ в PostgreSQL.
- Отдельная транзакция claim + result + processed_at;
  SKIP LOCKED распределяет строки, а не обеспечивает сам по себе
  внешнюю уникальность.
- Ошибка handler учитывается только при commit её записи;
  отказ SQL откатывает транзакцию. failed — не lost.
- Стабильный ключ должен переживать повтор/перезапуск отправителя;
  новый ключ означает новую операцию. В реальной системе область
  уникальности, срок хранения и политика повторов согласуются отдельно.

Техническая панель показывает job/outbox/result counts,
условный журнал событий с порядком (не реальные timestamps),
ключ, ID, hash/payload при раскрытии. Указать, что модель отображает
семантику, а не измеряет конкурентность, задержки или PostgreSQL.
Валидация расширенного ввода соответствует реальному /jobs:
text 1–2000 символов непустой; ASCII key 10–128, без пробелов,
один ключ; не нормализовать payload так, чтобы скрыть конфликт.
Старый свободный учебный ввод можно оставить только как
отдельный технический режим, не дублировать UI.

## 6. Приёмка и доказательства

P1 browser: RJ01–RJ12, включая возврат существующего ID, видимый
неизвестный статус отправителя, отсутствие двойного результата,
отличие queued/done/failed, повтор с новым ключом (новая запись),
сброс, отмену, мобильный экран 390px, клавиатуру, отсутствие
неожиданных запросов и ошибок, вложенный URL mount, CTA/возврат.
Неподдерживаемые действия disabled с понятной причиной.
Не объявлять RJ06/RJ08/RJ10 доказанными на реальной БД по результату
браузерной модели. Доказательства из README.md показывать с датой.

P1 evidence: переиспользовать существующие реальные проверки и явно
подписать, что подтверждают. Если доступен изолированный PostgreSQL
и .NET, повторить smoke и SQL-проверки, без использования клиентских
БД и без расширения публичного API. Если недоступен, сохранить
исторические факты, не выдумывать новый результат.

P2 evidence — при отдельной задаче: управляемая потеря HTTP-ответа
после commit, прерывание процесса между claim/commit, разрыв SQL
во время транзакции, контролируемые handler failures до terminal.
Нужен тестовый-only failpoint/прокси и наблюдение через отдельное
соединение; не считать SQL primitive test полным E2E.
Фиксировать обе стороны, ID, количество строк, result, processed_at,
attempts, восстановление и версию кода. Не добавлять failpoint
в публичный или production endpoint. Внешние эффекты — отдельная
задача, зависящая от контракта получателя.

После реализации — фактические скриншоты, ревью Codex и ручная
приёмка. Затем обновить только Reliable Jobs в COMMERCIAL-HANDOFF.md
и Engineering. Не рекламировать P1 до приёмки.
